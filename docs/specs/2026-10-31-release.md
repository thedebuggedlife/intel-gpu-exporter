# Release design

This spec covers the release work on the roadmap in issue #1, across two pull requests:

- **PR 6:** Dependabot, auto-merge, release-please, the release workflow, the vulnerability gate and attestations.
- **PR 7:** the weekly rebuild, `image.lock`, the failure tracking issue and SARIF upload.

The README and `SECURITY.md` are PR 8. The first release, `1.0.0`, follows the docs. Hardware validation has already run, before the first publish, on an image built from `main`, and the results are in a comment on issue #1. Anything hardware shows later ships as an ordinary release.

## Intent

The exporter should stay patched without anyone doing routine work. A dependency update or a rebuilt base package should become a versioned, scanned, attested image, with a reviewable diff of what changed.

Automation that can publish on its own is only acceptable if it can't publish the wrong thing. So the design starts from what must never happen, and every safety property has a stated mechanism and a proof.

### Goals

- Dependency updates and scheduled rebuilds produce versioned releases with no manual steps.
- The image pushed is the exact image that was tested and scanned.
- Nothing is published until publishing is deliberately switched on.
- Automated releases rely on automated validation alone. A security patch never waits for hardware testing: if a release breaks on real hardware, users report it and the fix goes out the same way.
- The first release is a stable `1.0.0`. Hardware validation is not a release gate: it ran once before the first publish, and no release waits on it.

### Non-goals

- arm64 images. `linux/amd64` is the only target.
- Signing images with cosign. Provenance and an SBOM are the attestations for now.
- Scanning inside `intel_gpu_top`. See "What the gate can't see".

### Anti-goals

- A release job that builds a second image after the tests pass.
- A published `X.Y.Z` that later changes.
- `latest` pointing at a release candidate.
- Upstream text deciding a version number.

## Safety requirements

| # | Requirement | Mechanism | Proof |
| --- | --- | --- | --- |
| 1 | Merging PR 6 publishes nothing | `PUBLISH_ENABLED` is unset, which means off. While off, release-please runs with `skip-github-release`, so it creates no tag or release, no release PR gets auto-merge, and the push job is skipped | Static workflow test; the repository variables listed before merge; "After merge" step 1 |
| 2 | A major version needs a person | Auto-merge refuses a release PR whose major version is above the manifest's, or above 1 on the first release. It turns off any auto-merge already enabled and requests review instead | Simulation below; unit tests with a fake `gh` |
| 3 | `latest` moves only on a stable release | `scripts/release.py` computes the tag list. A prerelease gets only its exact tag | Unit tests for every case; the rehearsal for a stable release on a real registry |
| 4 | Published `X.Y.Z` is never overwritten | The push reads the tag first. A different digest there fails the run | Unit tests with a fake `skopeo` |
| 5 | A failed gate publishes nothing | The push is a separate job that `needs` the gate, the gate holds no write permission, and the GitHub release stays a draft until the push succeeds | Static workflow test; forced failure after merge |

## The publish switch

`PUBLISH_ENABLED` is a repository variable, and publishing is on only when it is `true`. Case doesn't matter, because GitHub's `==` ignores it. Unset means off, so merging PR 6 needs no setting at all. The coordinator flips it with `gh variable set`, with no code change.

| | Switch off | Switch on |
| --- | --- | --- |
| Release PR | Opens and updates | Opens, updates and gets auto-merge |
| Merged release PR | Stays pending: no tag, no release, no new release PR | Tag and draft release |
| Publish | Skipped | Runs after the gate |
| Dependabot auto-merge | Runs | Runs |

Dependabot auto-merge deliberately ignores the switch. Merging a dependency update publishes nothing by itself, and it lets the update path be proven before the first publish.

A person can still merge the release PR while the switch is off. Nothing follows, because the release is only created once the switch is on. release-please also opens no new release PR while a merged one is pending.

Turning the switch on takes effect on the next push to `main`, or on dispatching `release` from `main`.

**What the switch guards against.** It stops automation and accidents, not a maintainer with write access, who could edit a workflow on a branch and run that copy. That is outside this design, because that person can also change the switch. As a guard against accidents, the `release-please` and push jobs also require `github.ref == 'refs/heads/main'`, so a dispatch from another branch can't publish or burn a version. release-please always targets the default branch, so without that check, such a dispatch would create a tag and a draft that nothing pushes. `vars` also resolves organisation variables, so the check for an unset switch includes those. There are none today.

## Versions

release-please runs from `release-please-config.json` and `.release-please-manifest.json`, with `release-type: simple`, so there is no version file to maintain. `version.txt` doesn't exist, and release-please skips a missing one.

```json
{
  "bootstrap-sha": "1f93e79577587b83692f44ccef99ee1f99d7df12",
  "packages": {
    ".": {
      "release-type": "simple",
      "initial-version": "1.0.0",
      "draft": true,
      "force-tag-creation": true,
      "include-component-in-tag": false
    }
  }
}
```

The manifest starts as `{".": "0.0.0"}`. A manifest entry is what makes release-please look for a previous release, fail to find one and stop at `bootstrap-sha`.

**Bootstrap.** `1f93e79` is the last of the fork's setup commits. The next commit is PR #3, so the first changelog starts there and reads no upstream history. Upstream's 11 `feat:` and `fix:` commits stay out.

Tested by running release-please's real `Manifest` code over this repository's real history with only the GitHub API stubbed. The results are the same on 17.6.0, the version locked by `release-please-action` v5.0.0, and on 17.11.2. The harness was a one-off and isn't in the tree, so this table is its record.

| Scenario | Result |
| --- | --- |
| First run | `1.0.0`, with the four `feat:` PRs #4 to #7 as the whole changelog |
| Release flags at `1.0.0` | `draft` and `forceTag` true, `prerelease` false |
| `1.0.0` + `fix(deps):` | `1.0.1` |
| `1.0.0` + `feat:` | `1.1.0` |
| `1.0.0` + `feat!:`, or `BREAKING CHANGE:` in a `<blockquote>` | `2.0.0`, which the guard holds for review |
| `1.0.0` + `chore(deps):` or `ci(deps):` only | No release PR |
| `1.0.0` is a tagged draft, or is found only as a tag | Next is still `1.0.1`, so a burned version doesn't confuse later runs |
| `Release-As: 3.0.0` in a commit body | `3.0.0`, which the guard holds for review |

**No release candidates.** Automated validation is the standard for every release. The tests, build, image test and scan run before each publish, and a problem only real hardware can show gets reported by users and fixed in the next release.

The `1.x` compatibility contract applies from the first publish. Hardware validation ran before that, on an image built from `main` at `dfaca4b` and on one Intel iGPU with two video engines and a single GT, so the results apply to that image and that hardware rather than to the published image. Three items stayed open: `igpu_rc6` reads 0 from both exporters, a 5-minute run can't rule out slow memory growth, and `igpu_gt_*` is still tested only against a hand-written fixture. A later hardware finding that needs a contract metric changed means `2.0.0`, and anything else is a patch. If the gate fails on the first release, `1.0.0` is burned and the first public version is `1.0.1`.

**The release guard.** `scripts/release.py check <version>` refuses:

- anything that isn't `X.Y.Z` or `X.Y.Z-rc.N`
- when given `--manifest`, a major version above the one in that manifest. From `0.0.0`, the first release, the limit is major version 1, so a stray `BREAKING CHANGE:` can't make it `2.0.0`

The push applies only the format rule, because a person merging a major release PR is the decision. release-please won't produce an `rc` by itself, but `Release-As:` could, so the tag rules still cover one.

When auto-merge is refused, the job holds the PR with `scripts/hold-for-review.sh`, as described under "Holding a PR", and passes. A failed run would fire PR 7's tracker on every push to `main`, and a refusal isn't a failure.

**Commit bodies are input.** release-please parses the whole squash commit, and merges here use the PR body as the commit body. A line starting `Release-As:` sets the version, a line starting `feat:` adds a changelog entry, and `BREAKING CHANGE:` counts even inside the `<blockquote>` Dependabot uses for upstream release notes. PR bodies #3 to #7 contain no such lines.

So Dependabot auto-merges set a fixed commit body, and upstream text doesn't reach `main` that way. A person merging a held Dependabot PR uses the same default, so they should clear the body in the merge dialog, and a maintainer writing a PR body should avoid those lines. `CLAUDE.md` records both. If it's missed, `BREAKING CHANGE:` gives a major release PR, which the guard holds for review. A `Release-As:` within the same major version wouldn't be caught, and that's accepted, because a person already reviewed that PR. Changing the repository's squash message to blank would close this, but it would drop PR bodies from history on every merge.

## Dependabot

`.github/dependabot.yml` updates `pip`, `docker` and `github-actions` weekly, each with `cooldown: default-days: 7`. Security updates aren't affected by the cooldown. There are no `groups`, so each PR has one dependency and its metadata is unambiguous.

| Ecosystem | Commit prefix | Release |
| --- | --- | --- |
| `pip`, `requirements.txt` | `fix(deps)` | Patch |
| `pip`, `requirements-dev.txt` | `chore(deps)` through `prefix-development` | None |
| `docker`, the Alpine digest | `fix(deps)` | Patch |
| `github-actions` | `ci(deps)` | None |

**Telling the two requirements files apart.** Dependabot's pip parser puts a requirement in the development group when its filename contains `dev`, and `prefix-development` applies to that group, so one `pip` entry is enough.

**The hash lock.** `requirements.txt` has multi-line `--hash` entries. Dependabot's `RequirementReplacer` keeps a hash block and its separator style, based on reading the source. The pin is old enough that the first scheduled run should open a real update, which is held for review as a minor bump. Check that both hash lines changed and the backslash layout survived. `pip install` in CI enforces the hashes, so a wrong one fails the required checks.

The Dependabot CLI could prove this before merge, but this environment blocks running the downloaded binary, and nothing publishes while the switch is off, so the first real PR is a safe proof.

## Auto-merge

`.github/workflows/dependabot-auto-merge.yaml` decides each Dependabot PR.

| Update | Decision |
| --- | --- |
| Patch | Merge once required checks pass |
| Alpine digest only | Merge once required checks pass |
| Minor or major | Request review |
| Security, patch or minor | Merge once required checks pass |
| Security, major | Request review |
| Anything else, including an unknown `update-type` | Request review |

`scripts/dependabot_policy.py` holds this table, so it has unit tests. A security update means `alert-state` is `OPEN` with a `ghsa-id`. If the alert lookup finds nothing, the update falls back to the ordinary rules, which fails safe.

**Docker updates.** `update-type` can't identify a digest update. Real Dependabot PRs show a digest-only bump with `update-type: version-update:semver-patch` on `alpine:3.24.3` and no `update-type` at all on `alpine:latest`. A digest-only bump is recognised by its title, `` bump alpine from `294b683` to `be26560` ``, which has backticked hashes where a tag change has versions. Any other Docker update must stay on the same `X.Y` to merge, whatever `update-type` says, so a move from `3.24` to `3.25` waits. That matters because it can change the Python version.

**Holding a PR.** `scripts/hold-for-review.sh`, used here and by `release.yaml`, first turns off any auto-merge already enabled, then asks for a review from `avargaskun` through the REST `requested_reviewers` endpoint, and GitHub emails a requested reviewer. Dependabot's own `reviewers` option is deprecated, and `CODEOWNERS` would request review on PRs that auto-merge too, so this notifies only when a person is actually needed. GitHub sends that email if the account's "Participating" notifications include email.

Turning auto-merge off is what makes the hold real. GitHub only does it by itself when someone without write access pushes, and the app has write access. So a release PR armed at `1.0.1` and updated to `2.0.0` while checks run, or a Dependabot PR that moves from patch to minor, would otherwise still merge unreviewed. The script reads `autoMergeRequest` first, so a PR that isn't armed passes. Any real failure fails the job, because hiding it could leave a PR armed.

**A held security major** can't ship something vulnerable unnoticed. If the finding is fixable and critical or high, the gate stops every release until it is handled.

**The trigger is `pull_request_target`.** GitHub restricts secrets for Dependabot on `pull_request`, but on `pull_request_target` only when the base ref was created by Dependabot, which `main` wasn't. So:

- The workflow reads the ordinary Actions secret, and the Dependabot secret store stays empty.
- The workflow and its Actions come from `main`. On `pull_request`, a PR bumping `create-github-app-token` would hand the key to the new version before review.

That trigger makes the job's guards essential:

- It runs only when the PR's author is `dependabot[bot]` and the head repository is this one.
- It never checks out PR code. Its checkout takes no `ref`, so it gets `main`.
- `dependabot/fetch-metadata` verifies the author and commit signature, and fails on anything else.

GitHub's docs don't say whether `vars` reach this event, so the job checks that the App ID and key are non-empty before using them, and fails if not. If the secret or variable turns out to be missing, the fix needs no workflow change, because Dependabot secrets use the same name. Run this, which reads the key from its file without printing it:

```bash
gh secret set RELEASE_BOT_PRIVATE_KEY --app dependabot \
    --repo thedebuggedlife/intel-gpu-exporter < /path/to/private-key.pem
```

**Why the app token.** An auto-merge enabled by `GITHUB_TOKEN` produces a push to `main` that starts no workflows, so release-please would never see the fix. Merges have to run as the app.

The merge command sets `--subject` to the PR title and a fixed `--body`. The title is passed through an environment variable, never interpolated into the script.

## Workflows

| File | Runs on | Can write |
| --- | --- | --- |
| `ci.yaml` | PRs, pushes to `main` | Nothing |
| `gate.yaml` | PRs touching release inputs, `workflow_dispatch`, `workflow_call` | Nothing |
| `publish.yaml` | `workflow_call`, `workflow_dispatch` | Its `push` job: packages and releases |
| `release.yaml` | Pushes to `main`, `workflow_dispatch` | Through the app token, and its job calling `publish.yaml` |
| `dependabot-auto-merge.yaml` | `pull_request_target` | Through the app token |
| `rebuild.yaml` | Weekly schedule, `workflow_dispatch` | Through the app token, its `sarif` job's `security-events`, and its `track-failure` job's `issues` |

Every job declares `permissions:`, and every Action is pinned by full commit SHA with the version in a comment. A called workflow can only reduce the `GITHUB_TOKEN` permissions of the job calling it, so the `publish` job in `release.yaml` must grant `packages: write` and `contents: write` itself. Those two jobs are the only places that may grant `packages: write`.

The app token comes from `actions/create-github-app-token`, using the repository variable `RELEASE_BOT_APP_ID` and the secret `RELEASE_BOT_PRIVATE_KEY`, and requests only the permissions each job needs. The action marks `app-id` as deprecated in favour of `client-id`, which shows as a warning. It keeps working, and moving means a new repository variable, so that waits for a major bump of the action.

The app has `contents`, `issues`, `pull_requests`, `statuses` and `workflows` write, and `checks` and `vulnerability_alerts` read. That covers release PRs, labels and the alert lookup. `workflows: write` is what allows merging an Action update, so the Dependabot auto-merge token requests it. It has no `packages` permission, so pushing uses `GITHUB_TOKEN` in the one job that declares it.

### `release.yaml`

Four jobs:

- **`release-please`** creates an app token, because a PR opened by `GITHUB_TOKEN` starts no CI, so its required checks would never report. It runs `release-please-action` with `skip-github-release` set to `vars.PUBLISH_ENABLED != 'true'`.
- **`auto-merge`** runs after it, only if the switch is on. It finds the open release PR by its branch, `release-please--branches--main`, runs `release.py check --manifest` on its version, and then either runs `gh pr merge --auto --squash` or holds the PR with `scripts/hold-for-review.sh`. Looking the PR up, rather than using the action's output, picks up a PR that already existed when the switch was flipped. `gh pr list --head` also returns a fork's PR from a branch of the same name, and stops at 30 results, so anyone could get a fork PR armed by naming a branch `release-please--branches--main`, or hide the real one behind 30 of them. The lookup is REST's `pulls?head=<owner>:<branch>`, which filters on the server. The owner matters: GitHub ignores a `head` with no owner and lists every PR.
- **`publish`** needs only `release-please`, runs if `release_created` is true and the switch is on, and calls `publish.yaml` with the tag. It doesn't need `auto-merge`, because a failure there would otherwise strand a created release: `release_created` is true only in the run that creates it.
- **`track-failure`** reports any failed job, as described under "Failure tracking".

The workflow has a `concurrency` group without `cancel-in-progress`. If a queued run is dropped, the next one still finds the merged, pending release PR, because releases come from PR labels rather than from the commit that triggered the run.

### `gate.yaml`

The gate is a single read-only job, used for pull requests, dry runs and releases alike. Its token is `contents: read`, and it holds no secret.

1. Check out the ref. Run `ruff` and `pytest` through a composite action shared with `ci.yaml`, so the suites can't drift.
2. Build once, for `linux/amd64`, with `--no-cache` and `--pull`, to an OCI archive with `provenance: mode=max` and an SBOM. BuildKit and the SBOM generator are pinned by digest, because they produce the attestations.
3. Convert the archive with `skopeo` to a docker-archive and `docker load` it.
4. Assert that the loaded image ID equals the digest of the archive's image config.
5. Run `scripts/test-image.sh` on that image.
6. Run `scripts/image_lock.py` on the loaded image and upload the `image-lock` artifact.
7. Run grype on the archive and apply the gate, including an assertion that the image ID grype reports is that same config digest. Upload its SARIF as the `sarif` artifact, even when the scan fails.
8. Rehearse the push against a `registry:2` service container on `localhost`, pinned by digest, as `v999.0.0`, which is newer than any real version, then assert the registry holds exactly `999.0.0`, `999.0` and `latest`. This runs the real `skopeo` on a real runner with no credentials.
9. Upload `image.tar` as an artifact and output the index digest.

The rehearsal uses the same code path as a real push, so it adds no way around a guard: `release.py` has no flag to skip a check or to disable TLS. It turns TLS verification off only when the repository's host is `localhost`, which is why a rehearsal can't reach a real registry insecurely.

### `publish.yaml`

`gate` runs first. `push` `needs` it, and also requires `vars.PUBLISH_ENABLED == 'true'` and `github.ref == 'refs/heads/main'`.

1. Download the artifact and assert its index digest matches the gate's output.
2. Attach the gate's `image.lock` to the draft with `gh release upload --clobber`. This comes before the push because a draft isn't public, so a failed upload leaves nothing to clean up, and `--clobber` lets a re-run finish.
3. Run `scripts/release.py publish`: the release guard, then the tag check, then the copies.
4. Publish the GitHub release with `gh release edit <tag> --draft=false`.

Its token has `packages: write` and `contents: write`. `workflow_dispatch` on this file is the retry path. Dispatched from `main`, it takes an existing tag, rebuilds at that tag, and still respects the switch.

### Dry runs

`gate.yaml` is the dry run. It has no push step and no write permission, so dispatching it can't publish. It also runs on pull requests that touch `Dockerfile`, `.dockerignore`, `requirements.txt`, `intel_gpu_exporter/**`, `scripts/**`, the ignore file or the gate and publish workflows. It's a useful signal, not a required check: making it required is a repository setting, and the release gate is the safety. It's the only way to run the whole pipeline before merge, because `workflow_dispatch` needs the workflow on the default branch.

## One image

The image pushed must be the one tested, and these constraints shape how:

- `load: true` can't carry attestations into Docker's classic image store, which the runners use.
- `docker load` rejects an OCI archive, with `does not contain a manifest.json`.
- A second exporter in the same build fails, because the docker exporter rejects the attestation manifest list.
- Rebuilding from cache isn't identical in principle, and `igt-gpu-tools` is unpinned.

So the OCI archive is the single artefact, and everything else derives from it.

| Step | Tool | Verified locally with `skopeo` 1.13.3, the runner's version |
| --- | --- | --- |
| Run the tests | `skopeo copy oci-archive: docker-archive:`, then `docker load` | Loaded image ID equals the OCI config digest |
| Scan | `grype oci-archive:` | Reports the same manifest digest and image ID |
| Push | `skopeo copy --all --preserve-digests` | Pushed index digest equals the archive's, with the attestation manifest present |

After each copy, the push re-reads the tag and compares `sha256` of the raw index with the expected digest. A mismatch fails the run.

## Tags

`scripts/release.py` works out the tags from the version and the existing `v*` git tags.

| Version | Image tags |
| --- | --- |
| `1.2.3`, the newest stable | `1.2.3`, `1.2`, `latest` |
| `1.2.3`, with `1.3.0` existing | `1.2.3`, `1.2` |
| `1.2.3`, with `1.2.4` existing | `1.2.3` |
| `2.0.0-rc.1`, if `Release-As:` forces one | `2.0.0-rc.1` |

Anything not matching `X.Y.Z` or `X.Y.Z-rc.N` is refused. The comparison with existing tags keeps a retry of an older tag from moving `latest` backwards.

**Never overwritten.** Immediately before pushing, `skopeo inspect --raw` reads `X.Y.Z`:

| Result | Action |
| --- | --- |
| Exists with a different digest | Fail |
| Exists with this digest | Continue, because this is a re-run finishing an interrupted push |
| `manifest unknown` or `name unknown` | Push |
| Anything else | Fail, so an auth or network error can't look like "absent" |

`skopeo` 1.13.3 exits 1 for a missing tag, so the check reads the error text rather than the exit code. GHCR answers `MANIFEST_UNKNOWN` for an authenticated read of a package with no images, confirmed with a read-only request, so the guard doesn't block the first publish. The exact tag goes first and `latest` last.

## When the gate fails

release-please creates the tag and release before the gate runs, so:

- The release stays a **draft**, which isn't public.
- The **tag stays.** release-please needs it to find the previous release, because draft releases otherwise have no tag and the next changelog would include all history. That's what `force-tag-creation` is for.
- **The version is burned.** It never gets an image, and the next releasable commit takes the next number. A tag is never moved, so a version always means one commit.

`Fixing forward` is the normal response. The draft can be deleted afterwards, and the tag stays.

A transient failure, such as a registry outage, can be retried with "Re-run failed jobs". That should reuse the artifact, and the digest check above makes it safe. A retry through `workflow_dispatch` rebuilds, so if the first attempt pushed anything, the different digest fails it, which is correct: the exact tag already belongs to that first image.

**Nobody may be told.** GitHub's failure email goes to whoever triggered a run, and a release run is triggered by a bot. PR 7's tracking issue therefore covers `release.yaml` as well as the weekly rebuild. PR 6 needs no interim mechanism, because publishing stays off until PR 7 is merged.

## Vulnerability gate

**The scanner.** grype `0.121.0`, downloaded from its GitHub release and checked against a SHA-256 pinned in the repository: `64e07133d3486115de647a66581461dccf5c732748a0a3119077395565f15519` for `grype_0.121.0_linux_amd64.tar.gz`. The value matches both the published checksums file and GitHub's asset digest. Bumping it is a manual change: verify the release's `checksums.txt` with `cosign verify-blob` and its `.sigstore.json` bundle, then update the version and digest together. The vulnerability database is downloaded fresh on each run and isn't pinned, because new findings are the point. A failed download fails the gate.

**The rule.** `scripts/vuln_gate.py` reads grype's JSON. It fails on any match with severity `Critical` or `High` and `fix.state` of `fixed`, unless a live ignore entry covers it. grype's own `ignore` config has no expiry, which is why this is a separate step.

**The ignore file** is `grype-ignore.toml`, which the Python standard library can read:

```toml
[[ignore]]
id = "CVE-2026-12345"
reason = "Only reachable through a code path this image doesn't include."
expires = 2027-01-31
```

- An entry matches the vulnerability's ID or any related ID, so a CVE entry also covers its GHSA alias.
- `expires` must be a TOML date. An entry works through that day and stops the day after.
- An expired entry has no effect, and the gate names it in its output.
- A malformed entry, such as a missing reason or a date given as a string, fails the gate.

**Proving the gate fails.** The repository variable `SCAN_FORCE_FAIL=true` makes `vuln_gate.py` treat the scan as failed. It can only cause a failure, so it is safe to leave in place, and it gives the coordinator the forced failure "Definition of done" needs.

**Baseline.** On the image at `dfaca4b`, with today's database: 0 critical or high, and 4 medium and 1 low finding, none with a fix available.

### What the gate can't see

`intel_gpu_top` is copied into the image as a bare binary, with no package metadata, so scanners and the SBOM can't see it. A vulnerability in `igt-gpu-tools` won't fail this gate. `eudev-libs` and musl, which it links, are installed packages and are visible. `image.lock` records the tool's version and hash, so a change is reviewable, but a new vulnerability in an unchanged version stays invisible.

## Attestations

Provenance (`mode=max`) and an SBOM are generated by the one build and live in the image index, so the push carries them. Read them with `docker buildx imagetools inspect <image> --format '{{ json .Provenance }}'` and `'{{ json .SBOM }}'`. `mode=max` records build parameters but no secrets, and the build uses none.

## GHCR

The image is `ghcr.io/thedebuggedlife/intel-gpu-exporter`. New packages default to private. **After the first publish, the coordinator makes the package public.** Until then, pulls need authentication.

## Required checks and the app

`main` requires a PR and the checks `lint-and-test` and `image-test`, with no approvals, and `enforce_admins` on. The required check entries are bound to the GitHub Actions app, ID 15368. The app needs no bypass: it merges an ordinary PR whose required checks passed. CI runs on the release PR because the app opened it, and auto-merge waits only for required checks.

## PR 7

### Weekly rebuild

`.github/workflows/rebuild.yaml`, on a weekly schedule plus `workflow_dispatch`. Dependabot can't see Alpine packages or the `edge/testing` tool, so this job covers them. It runs on Wednesdays, after Dependabot's Monday run, so that week's `fix(deps):` updates have usually been released and the middle row below applies rather than a second release.

1. Call `gate.yaml`, which already builds with `--pull --no-cache` and runs the suite and the scan.
2. Download the `image-lock` artifact the gate produced.
3. Run `scripts/rebuild_pr.py`, which compares it as in the table below. A change opens a PR through the app token and enables auto-merge. It does nothing unless the commit this run built is still the tip of `main`: a re-run keeps its original commit, and a lock from an old build compared with today's `main` would look like a change.

The rebuild has one path to anything public, which is that PR. It calls no publishing workflow, grants no `contents` or `packages` write, and the app has no `packages` permission. A merged PR reaches a release only through `release.yaml` and the switch. Only `schedule` and `workflow_dispatch` start it, so a merge can't start another run. `update` and the SARIF upload run only from `main`, so a dispatch from another branch is a dry run.

| New lock compared with | Action |
| --- | --- |
| The committed file: same | Nothing |
| The committed file: different, and same as the latest published release's asset | `chore(deps): record image contents`, which merges with no release |
| The committed file: different, and different from that asset, or no published release has one | `fix(deps): update image packages`, a patch release through the ordinary path |

The middle row is what keeps "Never publish a release with no content change" true. Any release can pick up newer packages than the committed lock, and without that row the next weekly run would release an identical image. "Published" means not a draft, so a burned version doesn't count. While the switch is off, no release has an asset, so changes go into the waiting release PR, which is harmless.

The asset compared is the one on the highest stable version among published releases that have one, read from the release list rather than `releases/latest`. A retry of an older tag can move GitHub's "latest" backwards, and a release candidate doesn't move the `latest` image tag. An empty list is the only thing that means "no release", so a failed lookup fails the run rather than taking the `fix(deps):` row.

**One PR at a time.** The branch is always `rebuild/image-lock`, and the workflow's `concurrency` group stops two runs racing. While the switch is off the PR still merges and moves the committed lock, so a change isn't proposed twice, and an open PR is reconciled rather than duplicated:

| Open rebuild PR, and this run's result | Action |
| --- | --- |
| Changes more than `image.lock` | Hold it with `scripts/hold-for-review.sh`, whatever the table says. A person has changed it, so it is neither rewritten nor merged. If its newest commit is over a day old, also fail the run, because it's blocking the rebuild |
| The image matches the committed lock again | Close it and delete the branch. It would otherwise merge a stale record, and a `fix(deps):` title would release nothing new |
| Same lock, same row, newest commit under a day old | Arm it if it isn't armed, since a run can fail between opening and arming. CI doesn't re-run |
| Same lock, same row, newest commit over a day old | Fail the run, naming the PR, so the tracker reports it. It should have merged within the hour, so CI failed, it conflicts, or a person turned auto-merge off. It isn't armed again, because that would overrule the person |
| Different lock | Move the branch to one new commit on current `main` |
| Different row | Disarm, retitle and arm again. Auto-merge stores its subject when it's enabled, so an armed `fix(deps):` would otherwise keep that subject after the row changed |

The commit goes through the Git Data API, which needs no credentials on disk and moves the branch in one step, so a PR is never left with no diff. Force-moving the branch across a change to `main`'s workflow files doesn't need the `workflows` permission when the new commit's workflows match `main`, so the token asks only for `contents` and `pull-requests`. That was tested with a token lacking the `workflow` scope, including moving a ref from an older commit, on scratch refs.

A failed run is the only signal that reaches a person reliably, because a repeated review request may not notify anyone again. It costs one tracker comment a week until someone merges or closes the PR.

**The PR's text can't change a version.** The title is one of two constants. The body is a fixed sentence with no `:` in it, and auto-merge is armed with that title and body, so nothing generated reaches the squash commit. The lock's diff is the record of what changed.

`image.lock` detects change and is not a build input. A release can't be held to it, because `edge` drops old versions.

**Generating it.** `scripts/image_lock.py <image>` runs `docker create` and `docker export`, and reads four things from the exported filesystem, running nothing in the image:

| Line | Source |
| --- | --- |
| `apk <name> <version>` | The real apk database, `/lib/apk/db/installed`, `P:` and `V:` fields only |
| `python <name> <version>` | `dist-info/METADATA` in the venv, with normalised names |
| `tool igt-gpu-tools <version>` | `/usr/bin/intel_gpu_top.version` |
| `tool intel_gpu_top sha256:<hash>` | The binary |

Lines are sorted, one per fact, so a change is a one-line diff. The database's `t:`, `c:` and `C:` fields are a build time, a commit and a checksum, and they stay out. A missing or malformed source fails the gate rather than producing a short lock, which would read as a huge change.

**Determinism.** Two `--no-cache --pull` builds of the same commit gave different image IDs and a byte-identical lock. Everything else that differed between them was compiled `.pyc` files and `/var/log/apk.log`, which hold timestamps and aren't content. Adding one apk package changed exactly one line.

`gate.yaml` gains a step after the image test that runs it and uploads the `image-lock` artifact. `publish.yaml` downloads that artifact and uploads it as a release asset named `image.lock` before publishing the draft, so a published release always has its record. Commit the first `image.lock` by hand in PR 7, generated from a gate run, so the first weekly run doesn't release it. The lock isn't compared with `requirements.txt` in tests, because a Dependabot update changes that file and not the lock.

**The tool's version.** `intel_gpu_top` can't report one, and the final image has no package entry for it: the apk database is real, but it describes only what the final stage installed, and the binary is copied in. So the `tools` stage writes the first field of `apk list --installed igt-gpu-tools` to `/usr/bin/intel_gpu_top.version`, which `COPY` takes with the binary. Reading it from the same build is the only way it can't drift from the binary, because `edge` moves. `apk list` exits 0 when it finds nothing, so that stage also checks the file's contents. The version shows a new release of the tool, and the hash shows a package rebuilt under the same version.

**Forcing a rebuild with a change.** "Definition of done" needs one, and it takes no special code. Merge a `chore:` PR adding a small apk package to the `Dockerfile`, dispatch the rebuild, and revert afterwards. The change appears in neither the committed lock nor the last published asset, so it takes the `fix(deps):` row.

### Failure tracking

A failed run of `rebuild.yaml` or `release.yaml` opens one issue labelled `automation-failure`, or comments on the oldest open one. `scripts/track-failure.sh` does this in a `track-failure` job that `needs` every job that can fail. It finds the issue through the REST list rather than `gh issue list --label`, which goes through search and can miss an issue opened seconds earlier. Nothing closes the issue automatically, so a person always confirms the fix.

The job can't use `if: failure()`, because that misses a timeout. It runs on `always()` and checks `needs.*.result` for `failure` or `cancelled`. Measured on real runners:

| What happened | `needs.<job>.result` | A job with `if: failure()` |
| --- | --- | --- |
| A job hit `timeout-minutes`, directly or in a called workflow | `cancelled` | Skipped |
| A called workflow failed, including one called by another | `failure` | Ran |
| A `continue-on-error` job failed | `success` | Not applicable |
| A person cancelled a started run | `cancelled` | Not applicable |
| A queued run was dropped by `concurrency` | The run has no jobs | Not applicable |

**Cancelled runs.** Neither workflow uses `cancel-in-progress`, so a run `concurrency` cancels was only queued. It never starts a job, so it reports nothing, and that's right: the newer run does the same work. A cancelled job in a run that started is a timeout or a person, and those two look the same, so both are reported. A timeout must not be hidden, and one comment after a deliberate cancel costs little.

**Flooding and masking.** Each failed run adds one comment. `track-failure` shares one job-level `concurrency` group across both workflows, so two failing together can't both open an issue. It uses the run's own `GITHUB_TOKEN`, so a problem with the app can't stop it, and it has no `continue-on-error`, so a tracker that fails stays red beside the original failure instead of hiding that nobody was told. It runs after everything else, so it can't block a release. The log names the run before any API call. A failed lookup of open issues fails without creating one, so an outage can't open a duplicate.

The issue body mentions the maintainer, because otherwise a bot-opened issue reaches only people watching the repository. An assignee would do the same, but assigning can fail and a mention can't.

Keep the permission out of the gate, so `gate.yaml` stays read-only: the reporting job sits in the calling workflow.

### SARIF

`gate.yaml` also writes `grype -o sarif` and uploads it as an artifact even when the scan fails, which is when it matters most. `rebuild.yaml` has a separate job that runs with `if: always()` on `main`, uploads it with `github/codeql-action/upload-sarif`, pinned, with `security-events: write`, and sets `continue-on-error`. It can't trip the tracker, because `track-failure` doesn't `need` it. Only the weekly rebuild uploads: that gives code scanning a steady view without touching the release path.

### Known limits

These were found in review and accepted, because closing them would reopen the table or a settled path. Each one either alerts a person or is cheap to fix by hand.

- **A burned rebuild's content isn't proposed again.** If a `fix(deps):` rebuild merges and its release fails the gate, the committed lock already matches the image, so the first row applies and nothing retries it. A burned Dependabot update does heal, because it never moved the lock. The failed gate has already reached the tracker, and the way forward is to fix the cause and dispatch `publish` for that tag, or land any releasable commit.
- **An Alpine digest update can release no new content.** Dependabot's cooldown means the rebuild's `apk upgrade` usually gets those packages first, and the digest PR then lands as `fix(deps):`. The middle row covers rebuild PRs only, so "no release with no content change" holds for the rebuild, not for that Dependabot path.
- **A person closing a rebuild PR doesn't stop it.** The next run opens a new one while the lock still differs, at most one a week, because the image really has changed. A new lock also arms a PR that a person disarmed, since it's a new proposal. To stop proposals, disable the workflow.
- **A `fix(deps):` PR can merge just after a release that published the same lock.** The window is short, and the next run reconciles an open PR's row. The cost is one patch release with no change.

### What a schedule can't promise

This repository is a GitHub fork, and GitHub treats schedules in forks differently. It also disables schedules in a public repository after 60 days with no activity. A week with no change commits nothing, so a quiet stretch could stop the rebuild, and a schedule that doesn't fire can't report that it failed. Dependabot's weekly runs should keep the repository active, and "After merge" step 11 checks the first tick. If it stops, `gh workflow enable rebuild` turns it back on.

## Switching on

The coordinator's sequence, after PR 7 and PR 8 are merged:

1. Confirm the release PR's version is `1.0.0` and its changelog is right.
2. `gh variable set PUBLISH_ENABLED --body true --repo thedebuggedlife/intel-gpu-exporter`.
3. Dispatch `release` from `main`, or wait for the next push.
4. After the first publish, make the GHCR package public.

To stop publishing, delete the variable or set it to anything else. A release already past the gate will finish.

### After merge

Only these can't be proven earlier. They feed the Phase 6 runs in "Definition of done".

1. The merge opens a release PR for `1.0.0`, with no auto-merge, no tag, no release and no package.
2. The first Dependabot PR's run reads the Actions secret and `vars` on `pull_request_target`, and fetch-metadata's alert lookup works with the app token.
3. Dependabot handles the hash lock, tells the two requirements files apart, and resolves `docker.io/library/alpine:3.24@sha256:…`, which its parser normalises to `library/alpine`.
4. A held update sends the review-request email, and a held PR that was armed loses auto-merge.
5. The app enables auto-merge, and an Action update merges under branch protection.
6. An auto-merged `fix(deps):` starts `release.yaml`, which updates the release PR.
7. With the switch on: the release PR auto-merges, the draft and tag appear, `GITHUB_TOKEN` creates the GHCR package, the image gets `1.0.0`, `1.0` and `latest`, and the draft is published. This is the first real push to GHCR, and the first run of the artifact and digest passing through the nested `release.yaml`, `publish.yaml` and `gate.yaml` calls.
8. With `SCAN_FORCE_FAIL=true`, a release pushes nothing, leaves a draft, and PR 7's tracking issue opens. Run this after the first publish, because it burns the version it runs on.
9. A forced rebuild with a changed package produces a patch release, and one with no change publishes nothing. Also run one with no new package after a release that picked up newer packages than the committed lock, for the middle row.
10. "Re-run failed jobs" on a failed push reuses the artifact. Also check whether a re-run reads `vars` afresh or uses the original run's values. If it's the original, a re-run can publish after the switch is turned off, and that exception needs recording here. `image-lock` and `sarif` upload before the scan's result is known, so they set `overwrite`, and a re-run after a failed scan should confirm that works.
11. The first scheduled tick of `rebuild.yaml` fires, which a fork might not do until the workflow is enabled.
12. The app token moves `rebuild/image-lock` across a change to `main`'s workflow files without the `workflows` permission. That was only tested with a user token lacking the `workflow` scope. If it's refused, the run fails, the tracker reports it, and the fix is adding `permission-workflows: write`.
13. The rebuild PR gets CI, arms with its fixed subject and merges as the app, and that merge starts `release.yaml`.
14. `GITHUB_TOKEN` can create the label and the issue, the mention reaches the maintainer, and a second failure comments on the same issue. A timed-out gate can be proved by lowering `timeout-minutes` on a branch merged and reverted, but the run-state table above already shows the condition.
15. Code scanning accepts the first SARIF upload. Default setup is `not-configured`, which shouldn't affect an upload.
