# Exporter design

This spec covers the exporter work on the roadmap in issue #1, across three pull requests:

- **PR 2:** package layout, custom collector, generic engine parsing, no invented zeros, loud unknown input.
- **PR 3:** unified stream parser, `-p`, supervision, health metrics, shutdown.
- **PR 4:** configuration, multi-GT, client counts.

Image work, release automation and the README are separate roadmap items.

## Intent

The inherited script reports every missing value as 0, drops every engine after the first in each class, and shows a hung data source as a flat line. So a dashboard can't tell "idle" from "broken".

The goal is an exporter whose output can be trusted: a number means `intel_gpu_top` reported it, and a gap means it didn't. It stays a drop-in replacement, with the same metric names, port and environment variables.

### Goals

- Report every engine `intel_gpu_top` reports, under predictable names.
- Export only values present in the sample. A real 0 stays 0.
- Make a broken data source visible, both as a gap and as a warning.
- Keep the compatibility contract for all `1.x` releases.

### Non-goals

- Smoothing or averaging. Gauges stay last-sample, because smoothing hides short spikes.
- Replacing `intel_gpu_top` with direct PMU or fdinfo collection.
- Warning about new top-level sections the exporter doesn't use. They are ignored.

### Anti-goals

- A flat 0 that looks like an idle GPU when the data is missing.
- A contract metric silently changing what it measures.
- Warnings that fire on healthy hardware, which would make `igpu_parse_warnings_total` useless as an alert.

## Compatibility contract

These hold for every `1.x` release, and tests enforce them.

| Item | Contract |
| --- | --- |
| Port | Default `8080` |
| Path | `/metrics` |
| `REFRESH_PERIOD_MS` | Default `10000` |
| `DEVICE` | Optional `intel_gpu_top -d` filter |
| `DEBUG` | Enables debug logging; values `false`, `0`, `no` and empty mean off |

Every existing metric keeps its name, unit and meaning. All are gauges:

```text
igpu_engines_{blitter,render_3d,video,video_enhance}_0_{busy,sema,wait}
igpu_frequency_actual        igpu_frequency_requested
igpu_imc_bandwidth_reads     igpu_imc_bandwidth_writes
igpu_interrupts              igpu_period
igpu_power_gpu               igpu_power_package
igpu_rc6
```

**A contract metric is present whenever the source provides it.** The contract does not promise a series on hardware where `intel_gpu_top` doesn't report that value. The inherited 0 in that case was invented, so removing it doesn't break the contract, and this change carries no `BREAKING CHANGE` footer.

## What `intel_gpu_top` produces

These facts come from the `v2.3` source of `tools/intel_gpu_top.c` and from captures on a host with an Intel iGPU. Later sections rely on them.

**Framing.** Output starts with `[`. A comma follows a sample only if that sample had clients; otherwise only whitespace separates samples. A bounded run ends with `]`. An unbounded run stopped by `SIGTERM` ends with neither `]` nor a newline.

**Timing.** Observed over a pipe, not only read from the source: samples arrive one at a time, one period apart, and each ends at its closing `}` **with no trailing newline**. The newline comes with the next sample, so a line-based reader receives every sample one period late. A reader that takes chunks needs no workaround.

**Engine keys.** With `-p`, keys are `Name/N`, where `Name` is one of `Render/3D`, `Blitter`, `Video`, `VideoEnhance` or `Compute`. A class the tool can't name prints as `[unknown]`. Without `-p`, keys have no instance suffix, and each key combines all instances of its class.

**Sections.** A section is printed only if at least one of its counters is available:

| Section | When present |
| --- | --- |
| `period` | Always |
| `interrupts` | Always; the tool fails to start without it |
| `frequency`, `rc6` | Always on single-GT output. With `-p` on a multi-GT device they are replaced by `frequency-gtN` and `rc6-gtN` |
| `engines` | When any engine has a counter |
| `power` | Never on discrete GPUs. Absent when no RAPL power counter can be opened |
| `imc-bandwidth` | Only where the IMC counters exist |
| `clients` | Only when client data is available; absent from older output. `{}` when no client is active |

**Fields.** A printed section always lists all of its fields, even if one counter is unavailable, and the tool prints 0 for that field. So `"GPU": 0.000000` can be the tool's own placeholder. The exporter can't tell the difference and exports it as 0.

**Values.**

- The first sample covers about 50 ms whatever `-s` is set to, so its rates are noisy.
- `rc6` and `frequency` can read 0 on a parked GPU, and that is exported as 0.
- `rc6` read 0 throughout both captures, parked and at about 10% render load. The cause is unknown, and it stays on the hardware validation list. The exporter still reports what the tool says.

**Clients.** Observed under load. `clients` is keyed by client ID, and each entry has `name`, `pid`, `memory` and `engine-classes`. Every value is a string, including numbers.

The tool writes `name` without escaping it and replaces only non-printable characters. So a client whose name contains `"` or `\` produces invalid JSON. That is malformed output like any other: samples stop, and the watchdog restarts the child for as long as that client runs.

## PR 2: Package and metric model

### Layout

```text
intel_gpu_exporter/
  __init__.py
  __main__.py      entry point: logging, collector registration, HTTP server, stream loop
  metrics.py       sample normalisation, warnings, the collector
  stream.py        stream handling moved from the old script
```

- PR 3 adds `supervisor.py` and rewrites `stream.py`. PR 4 adds `config.py`.
- The image runs `python -m intel_gpu_exporter`, with `CMD ["-m", "intel_gpu_exporter"]`. `WORKDIR /app` puts the package on the import path.
- `intel-gpu-exporter.py` is deleted.

### Stream handling in PR 2

The stream handling moves across unchanged in behaviour, because PR 3 replaces it. That includes `IS_DOCKER`, both parser paths, the hardcoded port and the existing `DEBUG` truthiness. No `-p` yet.

The only edits allowed are those the default `ruff` rules require, plus calling the collector instead of `update()`:

- a module logger instead of the root logger
- f-strings
- string defaults for `os.getenv`

### Custom collector

An unlabelled `prometheus_client` `Gauge` exports 0 from the moment it is registered, and engine names are dynamic, so module-level gauges can't meet "no invented zeros". All output is built from the latest sample by a custom collector.

- `SampleCollector` lives in `metrics.py` and holds all state. There is no module-level metric state, so each test gets a fresh instance on its own `CollectorRegistry`.
- `update(sample)` runs on the stream side. It normalises the sample into a complete new snapshot of metric names, help text and values, and replaces the old snapshot by assignment. There is one writer, so no lock is needed. All warnings fire here, so they don't depend on scrape timing.
- `collect()` yields a `GaugeMetricFamily` per snapshot entry, plus `igpu_parse_warnings_total` as a `CounterMetricFamily`. It never mutates state.
- `describe()` returns an empty list. Without it, registration calls `collect()`, and the names are dynamic anyway.
- It registers on the default `REGISTRY`, so `process_*` and `python_*` metrics stay available.

Before the first sample, the only `igpu_*` series is `igpu_parse_warnings_total 0`. That 0 is a true count. PR 3 adds its health metrics alongside it.

### Engines

A key matches `^(.+)/(\d+)$`. The greedy class group makes `Render/3D/0` parse as class `Render/3D`, instance `0`, and `Render/3D` not match at all.

Each match publishes `igpu_engines_<class>_<instance>_{busy,sema,wait}`. Other fields in an engine entry, such as `unit`, are ignored.

The class name comes from one sanitising rule, applied to known and unknown classes alike:

1. Insert `_` between a lowercase letter and a following uppercase letter.
2. Lowercase the result.
3. Replace each run of characters outside `[a-z0-9]` with `_`.
4. Strip leading and trailing `_`.

| Key class | Result |
| --- | --- |
| `Render/3D` | `render_3d` |
| `Blitter` | `blitter` |
| `Video` | `video` |
| `VideoEnhance` | `video_enhance` |
| `Compute` | `compute` |
| `[unknown]` | `unknown`, with a warning |

The existing `_0` names follow from this rule with no special case. A class added to the known list later keeps its name.

Whether a class is known is decided on the **raw** name, against a fixed set of the five names above. So `Video-Enhance/0` warns as unknown, even though it sanitises to a known result.

Help text follows the existing wording, for example `Video Enhance 0 busy utilisation %`, derived from the sanitised class name.

**Keys that can't produce a series.** These warn and export nothing:

- A key with no instance suffix, such as `Video`. Mapping it to `_0` would change what a contract metric means, because the key combines all instances of the class. From PR 3 the exporter always passes `-p`, so seeing one means something is wrong. The warning should name `-p` as the likely cause.
- A key whose class sanitises to an empty string.

**Collisions.** Two keys can sanitise to the same metric name, for example `Foo-Bar/0` and `Foo_Bar/0`. Known classes are processed first, so an unknown class can never displace a contract metric. After that the first key wins, and each later key warns and exports nothing.

### Sections

| Field | Metric | Help |
| --- | --- | --- |
| `period.duration` | `igpu_period` | `Period ms` |
| `frequency.actual` | `igpu_frequency_actual` | `Frequency actual MHz` |
| `frequency.requested` | `igpu_frequency_requested` | `Frequency requested MHz` |
| `interrupts.count` | `igpu_interrupts` | `Interrupts/s` |
| `rc6.value` | `igpu_rc6` | `RC6 %` |
| `power.GPU` | `igpu_power_gpu` | `GPU power W` |
| `power.Package` | `igpu_power_package` | `Package power W` |
| `imc-bandwidth.reads` | `igpu_imc_bandwidth_reads` | `IMC reads MiB/s` |
| `imc-bandwidth.writes` | `igpu_imc_bandwidth_writes` | `IMC writes MiB/s` |

**Required sections:** `period`, `frequency`, `interrupts`, `rc6`, `engines`. A missing one warns.

**Optional sections:** `imc-bandwidth`, `power`, `clients`. A missing one logs once at INFO, doesn't warn and doesn't count, because absence is legitimate on some hardware. `clients` has no metrics until PR 4 but is listed here so that absence is handled the same way throughout.

**Fields.** A missing or non-numeric field in a section that is present warns and exports nothing for that field; the section's other fields are still exported. The tool always prints every field of a section, so this means a rename, which is the failure mode this work exists to catch. The same applies to `busy`, `sema` and `wait` in an engine entry. A numeric value is an `int` or `float`, excluding `bool`.

**Wrong shapes.** A sample, section or engine entry that isn't a JSON object warns and exports nothing for that part. `update()` must never raise on sample content, and `collect()` must never receive a value it can't render.

### Warnings

A warning is logged at WARNING level once per distinct key for the life of the process, and `igpu_parse_warnings_total` increases by 1 at that moment. So the counter equals the number of warnings logged since start. It is bounded, stays at 0 on healthy hardware, and is safe to alert on with `igpu_parse_warnings_total > 0`.

Distinct keys are raw names:

| Trigger | Key form | Exported |
| --- | --- | --- |
| Unknown engine class | `Foo/0` (each instance is its own key) | Yes, under the sanitised name |
| Key with no instance suffix | `Video` | No |
| Class that sanitises to nothing | `/0` | No |
| Name collision | the losing key | No |
| Required section missing | `frequency` | No |
| Field missing or non-numeric | `frequency.actual`, `engines.Video/0.busy` | No |
| Wrong shape | `sample`, `frequency`, `engines.Video/0`, `clients.<id>` | No |
| Client with no usable name | `clients.<id>.name` | No |
| Stream buffer overflow | `stream-buffer` | No |

The set of seen keys is not capped, because the key names come from a small fixed vocabulary in `intel_gpu_top`. Client IDs are the exception, and they only appear in a key if the tool's client shape changes.

## PR 3: Stream, supervision, health, shutdown

### Command

`argv` is a list and never goes through a shell: `intel_gpu_top -J -p -s <period>`, plus `-d <device>` when set.

### Stream parser

`stream.py` is rewritten as one decoder over a text buffer using `json.JSONDecoder.raw_decode`, and the `IS_DOCKER` branch and the `Dockerfile` variable are removed.

- Skip leading whitespace, `[`, `]` and `,` between values.
- Read `stdout` in chunks, never by line, because a sample's closing `}` isn't followed by a newline. A sample must reach the collector as soon as its closing brace arrives.
- Decode bytes with an incremental UTF-8 decoder using `errors="replace"`, so a character split across chunks survives and bad bytes can't raise.
- A top-level value that isn't an object goes to `update()`, which warns under the `sample` key. It isn't a sample, so it doesn't refresh the last-sample time, and a stream of such values still reaches the watchdog.
- Bound the buffer at 1 MiB. On overflow, drop the buffer and warn under the key `stream-buffer`.

`raw_decode` fails the same way on a truncated object and a malformed one, so the decoder waits for more data in both cases. Input Python refuses to decode, such as nesting too deep or an integer over the conversion limit, counts as malformed. There is no resynchronisation: malformed output stops producing samples, the watchdog restarts the child, and a new child gets a new decoder. An unfinished buffer is discarded on restart.

### Supervision

`supervisor.py` owns the child process. It uses three threads besides the HTTP server: `stdout` reader, `stderr` reader and watchdog.

- **`stderr`** is read continuously in chunks and logged line by line at WARNING level, so it can never fill and block the child. A line that reaches 64 KiB without a newline is logged as a piece, so memory stays bounded however long the line is. These lines do not count toward `igpu_parse_warnings_total`, which covers only what the exporter can't parse.
- **Timeout** is `max(3 × period, 30 s)`. It is measured per child, from the later of that child's spawn and the last sample, so a new child always gets a full timeout whatever happened to the one before it. It uses arrival time and a monotonic clock, never `period.duration`, because the first sample is about 50 ms long.
- **On timeout** the child gets `SIGKILL`, because a stopped process ignores `SIGTERM`. It is then reaped, and restarted the same way as any other exit.
- **On any exit**, whatever the exit code, the child is restarted with capped exponential backoff: 1 s, doubling to a cap of 60 s, reset when a sample arrives from that child.
- **A failed spawn**, such as a missing binary, takes the same path as an exit, and each new attempt counts as a restart. The exporter keeps running and serving `/metrics`.
- **Readers** are joined before the next spawn, each for at most 1 s, so a stray process holding a pipe open can't block a restart. A reader that outlives its join stops at its next chunk, so only the current child's output reaches the collector.

### Health metrics

| Metric | Type | Meaning |
| --- | --- | --- |
| `igpu_up` | gauge | 1 if a sample arrived within the timeout, else 0. Computed at scrape time from the age of the last sample overall, not per child |
| `igpu_last_sample_timestamp_seconds` | gauge | Unix time the last sample arrived. Absent until the first sample |
| `igpu_collector_restarts_total` | counter | Child restarts since start, for any reason. The first spawn doesn't count |
| `igpu_parse_warnings_total` | counter | As defined above |

**Stale data.** While `igpu_up` is 0, only these four metrics are served, so a hang shows as a gap rather than a flat line. The last sample is kept, so if samples resume the data returns at once. This is what reconciles "keep gauges last-sample" with "stuck values are a defect".

`igpu_up` depends on age alone. After the child exits, it stays 1 until the timeout passes, which avoids flapping on a quick restart. The first sample after a restart covers about 50 ms and is exported as it is.

### Shutdown

`SIGTERM` and `SIGINT` set a stop event. The child gets `SIGTERM`, then `SIGKILL` if it hasn't exited after 5 s. The process exits 0. No restart happens once the stop event is set.

The signal handlers only record the request. The main thread checks it in a timed join on the watchdog and sets the stop event itself, for two reasons: a signal taken by another thread doesn't wake an untimed join, and `Event.set()` can deadlock if a second handler interrupts it. The main thread then waits at most 10 s for the watchdog, so a child that survives `SIGKILL` in the kernel can't stop the process exiting.

If the watchdog ends with no stop requested, the exporter logs it and exits non-zero, so a restart policy that acts on failure brings it back.

### Tests

- Stream parser unit tests using the captures plus truncated and malformed fixtures.
- An end-to-end test running the exporter against a fake `intel_gpu_top` on `PATH` and scraping `/metrics`. It covers a normal stream, a hang (restart and `igpu_up` 0), an exit (backoff and recovery) and heavy `stderr` output.
- Port `8080` and path `/metrics` join the contract test.
- A sample whose closing brace has no trailing newline must be exported without waiting for the next one.
- After a hang and restart, a slow-starting child gets a full timeout.
- `stderr` with no newline stays bounded, as part of the heavy `stderr` test.

`main()` takes `port` and `timing` keyword arguments so that end-to-end tests can run on an ephemeral port with short timeouts. They are for tests only, so `python -m intel_gpu_exporter` has no new configuration. `LISTEN_PORT` arrives in PR 4.

## PR 4: Configuration, multi-GT, client counts

### Configuration

`config.py` reads the environment once at startup into a frozen dataclass.

| Variable | Default | Rule |
| --- | --- | --- |
| `LISTEN_PORT` | `8080` | Integer from 1 to 65535 |
| `REFRESH_PERIOD_MS` | `10000` | Integer from 1 to 2147483, because `intel_gpu_top` multiplies `-s` by 1000 into a C `int` |
| `DEVICE` | unset | Passed to `-d`. Empty counts as unset |
| `DEBUG` | off | Trimmed and case-insensitive: unset, empty, `false`, `0` and `no` are off. Anything else is on |

An invalid number prints one line naming the variable and its value, and exits non-zero before the port is bound or the child is started.

### Multi-GT

With `-p` on a multi-GT device, `frequency` and `rc6` are replaced by `frequency-gtN` and `rc6-gtN`, matching `^(frequency|rc6)-gt(\d+)$`.

- GT 0 fills the existing unlabelled metrics: `igpu_frequency_actual`, `igpu_frequency_requested` and `igpu_rc6`.
- Every GT, including 0, also appears in new labelled gauges: `igpu_gt_frequency_actual{gt="N"}`, `igpu_gt_frequency_requested{gt="N"}` and `igpu_gt_rc6{gt="N"}`. Plain `frequency` and `rc6` sections produce none of these, so single-GT output is unchanged.
- The label goes on new names only. Adding it to the existing names would change contract series.
- `frequency` and `rc6` remain required, and any `-gtN` section satisfies that. A sample with `frequency-gt1` but no `frequency-gt0` doesn't warn, and the contract metrics are simply absent.
- Field checks apply to each `-gtN` section as they do to the plain ones.

On a device with a separate media GT, GT 0 doesn't reflect media work, so `igpu_frequency_actual` stays low during transcoding. That is the expected meaning, and the labelled series show the rest. The README must say so.

There is no real multi-GT capture. `tests/fixtures/handwritten-multi-gt.json` is written by hand from the source, and replaced during hardware validation.

### Client counts

`igpu_clients_count{name}` is a gauge counting the entries in `clients` with that `name`. Entries are keyed by client ID, and several can share a name.

- A client name seen earlier but absent from a sample that has a `clients` section reports 0. That 0 is real: the sample says there are none. Remembered names last for the life of the process, with no cap, because they are process names on the host.
- If the sample has no `clients` section, no client series are exported, because the sample says nothing about them.
- No series appears until a client has been seen.
- An entry with no usable `name` warns under `clients.<id>.name` and isn't counted. A name is usable if it is a non-empty string of printable characters, so nothing reaches `collect()` that a scrape can't encode. An entry that isn't an object warns under `clients.<id>`.
- Client series follow the stale-data rule like every other sample metric, so they aren't served while `igpu_up` is 0.
- Without host PID visibility the series stays empty. That is expected, and the README must say so.

### Tests

- The contract test covers the configuration contract: the default port, the `REFRESH_PERIOD_MS` default, `DEVICE` and the `DEBUG` off values. They run against the real process, not `config.py`.
- `tests/fixtures/loaded.json` runs through `StreamDecoder` whole, byte by byte and split at awkward points. Its client and engine values are asserted too, including `igpu_engines_video_1_busy` above 0 while `Video/0` reads 0.
